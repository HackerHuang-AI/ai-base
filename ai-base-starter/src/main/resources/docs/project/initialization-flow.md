# 系统、租户与用户初始化流程

## 1. 定稿边界

- `ai-base` 是用户、租户、租户内组织/岗位/角色及用户端菜单目录的数据归属服务。
- `ai-operations` 是运营控制面，持有运营端自身的 `operation_menu`、运营角色及其授权关系，并通过 Dubbo 调用 `ai-base` 管理个人租户菜单和企业租户入驻。
- 个人租户使用平台统一维护的菜单配置；企业租户后续按租户角色配置菜单。
- 用户端菜单展示不等于接口权限。业务接口必须独立校验成员资格、角色和权限。

## 2. 系统首次部署初始化

首次部署执行系统初始化 SQL，只写入系统固定数据，不写入任何业务租户数据。

```text
初始化 ai_base
-> 用户端菜单目录 menu
-> 个人租户默认展示菜单 personal_tenant_menu

初始化 ai_operations
-> 运营超级管理员用户及其 operation_user_role
-> 运营角色 operation_role
-> 运营端菜单 operation_menu
-> 运营角色菜单关联 operation_role_menu
```

约束：

- 菜单编码和路由由研发发布时登记；运营侧只能配置已登记菜单的展示状态和排序，不可自定义路由。
- 初始化的两名运营超级管理员是运营级身份，不归属任何业务租户。
- 初始化 SQL 必须可重复执行或由 Flyway 版本控制，避免重复插入固定数据。

## 3. 个人空间注册与初始化

用户在用户端完成手机号注册后，由 `ai-base` 在同一事务内完成用户和个人空间初始化：

```text
创建或确认 base_user
-> 创建个人 tenant（tenant_type = 1）
-> 创建 tenant_user 成员关系
-> 初始化个人空间默认角色
-> 为注册者授予个人空间租户管理员角色
-> 返回登录/租户上下文
```

约束：

- 一个用户最多拥有一个有效个人空间。
- 个人空间的用户端菜单由 `personal_tenant_menu` 统一决定；个人空间管理员不能修改这份平台统一菜单。
- 注册或初始化任一步失败时，事务整体回滚。

## 4. 企业租户入驻与初始化

企业租户由运营端发起入驻；运营端调用 `ai-base` 的租户入驻能力，创建时必须指定首位租户超级管理员。

```text
运营端提交企业资料和首位管理员 user_id
-> 校验企业唯一标识及管理员用户有效性
-> 创建企业 tenant（tenant_type = 2）和 tenant_info
-> 创建首位管理员 tenant_user 成员关系
-> 初始化企业默认角色
-> 为首位管理员授予租户超级管理员角色
-> 返回企业租户信息
```

约束：

- 不支持“先创建企业租户，再由用户认领超级管理员”，避免无管理员和管理员抢占。
- 企业统一社会信用代码唯一；重复入驻由业务流程拒绝或转入运营处理。
- 企业租户超级管理员默认首位 1 名，最多 2 名，且任何时刻至少保留 1 名有效超级管理员。
- 个人空间不能直接转换为企业租户；需要新建企业租户后迁移或复制资源。

## 5. 租户成员与资源管理

企业租户超级管理员仅管理本租户内资源：

```text
成员准入与移除
-> 分配或回收租户角色
-> 管理组织、岗位和成员任职
-> 后续配置企业租户角色菜单
```

不能管理：

```text
运营超级管理员
-> 其他租户成员或资源
-> 用户端菜单目录 menu
-> 个人租户统一菜单配置 personal_tenant_menu
-> 运营端菜单 operation_menu
```

## 6. 菜单配置职责

| 菜单数据 | 所属模块 | 配置主体 | 作用范围 |
| --- | --- | --- | --- |
| `menu` | `ai-base` | 研发初始化 | 用户端系统菜单目录 |
| `personal_tenant_menu` | `ai-base` | 运营端通过 Dubbo 管理 | 所有个人空间 |
| `operation_menu` | `ai-operations` | 运营角色授权管理 | 运营端自身 |
| 企业角色菜单关联（后续） | `ai-base` | 企业租户超级管理员 | 当前企业租户 |

用户端登录后，前端经网关调用 `ai-base` 菜单查询接口。`ai-base` 根据可信登录上下文中的租户类型返回菜单：个人空间返回统一配置，企业租户后续返回角色授权菜单。
